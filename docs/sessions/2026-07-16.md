# Piloteer — Architectural Decisions & Roadmap
## Date: July 16, 2026

> This document is a personal reference to structure technical ideas, architectural decisions, and upcoming implementations. Each section describes a decision, **why** it was made, and the **research** that backs it.

---

## Section 1 — Architectural Decisions

---

### Decision 1: Remove the Idempotency Rule from the Prompt (Rule 7)

**Description:**
Remove any instruction like "do not repeat an action that already succeeded" from the Planner's system prompt. This logic is moved into Python code (Validator or LangGraph graph).

**Why:**
Negative constraints ("do not do X") compete with the model's *implementation priors* — the statistical patterns activated during token generation. Trying to suppress an already-activated path via a negation token is statistically unreliable. A simple Python `if` that checks whether the action was already performed is **100% deterministic and free of cost**.

**Research:**
- *Mechanistic Interpretability* (activation patching, logit lens): confirms partial suppression of negative constraints even when the model demonstrably "understands" the negation.
- *Instruction-following survey (2024)*: negative constraints have significantly lower compliance rates than positive constraints, invariant to encoding.

---

### Decision 2: Reformulate USER_TASK as a "Target State" Instead of an Imperative

**Description:**
Change how the task is phrased when sent to the Planner.
- ❌ `"Create a project named 'Piloteer Test'"`
- ✅ `"A project named 'Piloteer Test' must exist in the workspace"`

**Why:**
An imperative formulation has no clear stopping condition — the model can loop indefinitely. A target-state formulation activates training patterns related to *state verification* (before/after, like a software test), which guides the Validator to objectively confirm whether the task is complete.

**Research:**
- Same research base as Decision 1 (implementation priors, positive vs. negative constraints).
- Aligned with the classic *post-conditions* pattern in formal software engineering (Hoare logic contracts).

---

### Decision 3: Automatic Popup Dismissal

**Research:**
- *Mind2Web / WebArena production analysis (2026)*: officially lists "modal interruptions" as one of 6 unbenchmarked failure modes of web agents.
- Overlay study: the agent "proactively searches and clicks on elements labeled 'Reject All', 'Accept All'... to close banners and overlays."

---

### Decision 4: Pre-processing Module — Accessibility Tree Pruning

**Description:**
Within the  `preprocess_snapshot()` module, add a **2-step Python filter** that reduces the YAML tree from ~20,000 tokens to ~2,000 tokens before sending it to the LLM.


**Why:**
Complex web pages generate between 10,000 and 100,000 DOM tokens. Even the accessibility tree routinely exceeds 20,000 tokens (confirmed empirically on Plane). This causes:
1. `429` Rate Limit errors on Groq and Gemini.
2. Response times of 5+ minutes on local LLMs (Ollama/Qwen).
3. LLM attention loss: the model "sees" too many irrelevant elements and makes poor decisions.

**Research:**
- **Prune4Web (November 2025, published at AAAI 2026)**: reduces candidate elements by 25–50x, doubling grounding accuracy compared to unfiltered approaches.
- **FocusAgent**: reduces observation size by over 50% while matching baseline performance, and as a bonus reduces prompt injection attacks via popups.

---

### Decision 5: Pass Raw Technical Errors to the Planner (Validator Refactoring)

**Description:**
Modify `validator.py` to include the raw Playwright error in the `reasoning` field sent back to memory, instead of an abstract summary.
-  `"The action failed because the interface did not respond."`
-  `"TECHNICAL ERROR: pointer events intercepted by backdrop [class='bg-backdrop']. Cause: an overlay is blocking the target element."`


**Why:**
Without the raw error message, the Planner has no causal information to understand *why* its action failed. It therefore repeats the action identically. The Reflexion paper (91% success rate) bases its "reflections" on the **raw execution output** of tests, not on summaries. Additionally, overly binary feedback risks creating a **self-reinforcing error**: the model falsely concludes an approach will "never" work and stops retrying it.

**Research:**
- **Reflexion (Shinn et al., 2023)**: critical feedback is raw execution output, not self-introspection.
- **2026 study on binary feedback**: the risk of self-reinforcing errors in multi-step tasks.

## Section 2 — Agent Self-Correction Tasks

> These tasks cover utility actions the agent must perform correctly to fix its own state without crashing.

---

### Task A: Clear a Text Field Before Typing

**Problem:** When the agent types text into an already-filled field, the new text is appended to the old one instead of replacing it, producing a corrupted entry.


### Task C: Handle Dropdowns (Combobox / Select)

**Problem:** React/Vue comboboxes are not real HTML `<select>` elements. Clicking them opens a menu, but the options appear as new elements in the tree (new `ref` values) that the Planner does not yet know about.

**Solution:**
After clicking a combobox, always capture a **new snapshot** before selecting an option. The correct flow is: `click(combobox)` → `get_snapshot()` → `click(option_ref)`.
