# Piloteer — Weekly Session Log
## July 16–18, 2026

---

## Overview

This week marked a turning point for Piloteer. We moved away from experimental ideas
(multimodal vision, Ollama fallback, French codebase) toward a disciplined, research-backed
architecture. Every decision this week was driven by an observed failure, a research finding,
or a performance measurement — not intuition.

---

## 1. Architecture: From Multi-Step Planning to One-Step-Per-Iteration Loop

### What changed
Previously, the Planner generated a full sequence of steps in a single call. The agent
then executed all of them without re-evaluating the page state between steps.

We replaced this with a strict one-step-per-iteration loop:
- The Planner generates exactly one step.
- The Actor executes it.
- The Validator checks the result and updates memory.
- The graph loops back to the Planner with the fresh page state and the updated memory.

### Why
Multi-step plans fail silently. If step 2 navigates to a page that no longer exists,
steps 3 through 10 are meaningless — but the agent executes them anyway.

With one step per iteration, the Planner always reasons from the current real state of the
browser, not from a predicted future state that may never materialize. This is the
"hierarchical planner-executor" pattern validated in the WebArena and Mind2Web benchmarks:
agents that re-plan after every action outperform agents with fixed plans by a wide margin.

The memory fed back to the Planner after each step allows it to learn from failures
within the same task run — if a click failed, the next Planner call knows exactly why.

## 2. Prompt Engineering: Few-Shot Examples and Removing Negative Constraints

### What changed
We added concrete few-shot examples to the Validator system prompt, showing what a
correct JSON response looks like in both the success case and the error case.

We also audited all prompts for "do not" and "never" instructions and replaced them
with positive, actionable equivalents wherever possible.

### Why
Research on LLM instruction-following (2024–2026) consistently shows that negative
constraints are the weakest form of instruction. Under load — long context, concurrent
rules, complex reasoning — models tend to drop negative constraints first. A model told
"do not summarize the error" will summarize it anyway once other rules fill its attention.

Positive instructions define what to do, which is unambiguous. "Copy the exact raw error
text verbatim" is stronger than "do not paraphrase the error" because it tells the model
exactly what output to produce, not what to avoid.

Few-shot examples reinforce format compliance. The model sees a concrete target output
and is far more likely to reproduce its structure. This is especially important for the
Validator, whose JSON must contain exactly three specific fields with specific semantics.

## 3. Task Formulation: Target-State vs. Imperative

### What changed
The USER_TASK constant was changed from an imperative instruction to a target-state
description.

Before: "Create a project named Piloteer Test"
After: "A project named Piloteer Test must exist in the workspace"

### Why
An imperative instruction activates a "creation" prior in the model. It will attempt
to create the object even if it already exists, leading to duplicate entries and
infinite loops. This was observed directly in testing on Linear: the agent found the
existing project in the sidebar but still clicked "New project."

A target-state description allows the Planner to first verify whether the condition
is already satisfied. If the project exists, the agent can mark the task done without
taking any action. If it does not exist, the agent creates it. The Validator can then
evaluate the final page state against the target condition directly.

## 4. Error Handling: Raw Errors from Actor to Validator to Planner

### What changed
We introduced a reliable boolean flag `last_action_is_error` set by the Actor using
the MCP SDK's `result.isError` attribute. This flag is stored in the shared state.

The Validator prompt now conditionally includes an `ACTION ERROR` section only when
this flag is true. Inside that section, the Validator is instructed to copy the raw
error text verbatim into its reasoning field before adding its own diagnosis.

When there is no error, the error section is entirely absent from the Validator prompt —
no noise, no empty fields.

### Why



**Why pass the raw error to the Validator:**
The Validator's reasoning is stored in memory and read by the Planner on the next
iteration. If the Validator paraphrases the error ("the click failed"), the Planner
has no causal information — it does not know why it failed. The Planner may repeat
the identical action.

If the Validator preserves the raw error ("pointer events intercepted by backdrop
class bg-backdrop"), the Planner knows precisely that a modal overlay is blocking the
element and can decide to dismiss it first. This is the core principle of the Reflexion
paper (Shinn et al., 2023): self-correction works only when the agent has access to the
raw diagnostic output of its failed attempt, not a summary of it.

**Why filter the error section from the prompt on success:**
Sending the action result to the Validator on every step — even successful ones — adds
noise. The result text on success ("Command executed with no text output") carries no
information useful to the Validator. Removing it reduces token consumption and removes
a potential source of confusion. The Validator's judgment should rest entirely on the
visual comparison of the accessibility tree before and after the action.

## 5. Task Completion: Validator Double-Check and Planner Termination

### What changed
The Planner uses a special tool called `browser_finish_task` to signal that it believes
the task is complete. The Actor intercepts this tool call and instead of executing it,
sends an explicit message to the Validator asking for a final confirmation pass.

The Validator then evaluates the current page state against the USER_TASK goal and
returns `task_done: true` or `task_done: false`. Only a `true` from the Validator
terminates the loop.

### Why
Without a double-check, the Planner can declare success prematurely. The Planner reasons
from the accessibility tree snapshot, which may be slightly stale. The Validator sees
the same snapshot but reasons about it from the perspective of the user goal, not the
action sequence. These are two different evaluations.

The double-check also protects against the Planner's optimism bias: models trained on
task completion tend to declare success as soon as a plausible terminal state is reached,
even if key details are missing (the project was created but has the wrong name, for example).

The `task_done` field in the Validator output is evaluated against the target state
described in USER_TASK, not against whether the last step succeeded. These are
deliberately decoupled.

## 6.Tree Pruning: Level-1 Accessibility Tree Filtering

### What changed
A new module `utils/tree_pruner.py` was created. It is called in the Planner node
before building the LLM prompt. It filters the raw accessibility tree snapshot and
returns only the nodes the Planner can act on.

Nodes kept: buttons, links, text inputs, checkboxes, comboboxes, radio buttons, tabs,
menu items, sliders, search boxes, dialogs, alert dialogs, headings, and StaticText
nodes with a name longer than two characters.

Nodes removed: layout containers (group, region, list, listitem, row, none, generic),
decorative images, SVG elements, and empty or whitespace-only nodes.

### Why

**Why filter at all:**
The Playwright MCP accessibility tree for a typical SaaS page contains between 15,000
and 25,000 tokens. Gemini 2.5 Flash has a context window large enough to process this,
but the token cost per call triggers rate limits rapidly. When rate limits are hit, the
system falls back to Flash Lite, which produces lower quality reasoning. The root cause
of the observed incorrect behavior (agent ignoring existing projects, choosing wrong buttons)
was therefore not the model's capability but the rate limit forcing a downgrade.

Filtering the tree to interactive elements only reduces it to approximately 1,500 to
3,000 tokens — a reduction of 85 to 90 percent. Flash is no longer rate-limited.

**Why Level 1 only (no semantic filtering):**
Level 2 filtering would use a small LLM to score each remaining element for relevance to
the current sub-task and keep only the top candidates. This adds latency, cost, and a
dependency on a second model call. Level 1 filtering is deterministic, instant, and free.
It is implemented in Python with no external calls.

**Why this does not break the Planner's understanding:**
In the Playwright MCP accessibility tree, interactive elements already carry their text
label as their accessible name. A button reading "Create project" appears as
`button "Create project" [ref=e601]` — the label is part of the element, not a
separate StaticText node. Removing layout containers does not remove labels.

For the rare case where a meaningful description exists only as a standalone StaticText
(such as a popup message or a section description), the pruner retains it as long as
the text is longer than two characters, which covers all real descriptive content.

**Why dialogs and alertdialogs are always kept:**
These are the primary mechanism by which the page signals an obstruction or a
confirmation request to the agent. Removing them would blind the Planner to the most
critical state changes it needs to handle.
